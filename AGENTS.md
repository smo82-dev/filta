# Coding Agent Instructions

Before development, review [Token-Efficient AI Development](docs/TOKEN_EFFICIENCY.md) and follow its workflow for context retrieval, prompt-cache opportunities, focused changes, verification and durable handovers.

Repository code, current pull requests, existing project instructions and owner-approved decisions take precedence over generic optimisation suggestions. Caching is automatic and conditional; do not claim guaranteed cache savings. Never weaken tests, security, financial or production safeguards to reduce tokens. Never merge, deploy or publish without explicit owner authorisation.

## Scheduled dependency security intelligence — planned requirement

When the owner authorises implementation, add a scheduled, **read-only** GitHub Actions security-reporting workflow for this repository. This instruction documents the requirement; it does **not** authorise creating or activating the workflow in a documentation-only task.

- Schedule a daily scan at **07:00 Pacific/Auckland (New Zealand local time)** where practical. GitHub Actions cron is UTC and does not automatically adjust for NZ daylight saving; use a documented DST-safe strategy or report the timing limitation. Allow manual `workflow_dispatch` execution.
- Inspect the checked-in dependency manifests and lockfiles, and available GitHub Dependabot/security advisories, using the ecosystem-appropriate tools. Include direct and transitive **critical** and **high** vulnerabilities; identify CVE/GHSA, severity, affected package and installed/resolved version, patched version if known, and a primary advisory/fix URL. Never invent fixes or confuse manifest constraints with deployed versions.
- Emit a concise GitHub Actions job summary and dated, machine-readable report artefact. Distinguish newly reported advisories from previously seen issues, and explicitly flag incomplete scans, inaccessible alerts, missing locks or tools, and audit failures. Deduplicate rather than creating a new GitHub issue for every daily run.
- Use only the minimum permissions needed to inspect repository content and alerts (prefer `contents: read` and `vulnerability-alerts: read` where supported). Set all unrelated permissions to `none`. Never use write permissions, tokens with unnecessary scopes, repository secrets, production credentials or external services merely for reporting. If alerts are inaccessible, document the limitation; do not escalate permissions silently.
- Security monitoring is **report-only**: no dependency updates, lockfile writes, auto-fixes, pull requests, issue creation, release, merges, deployment, database operations or production changes. A nonzero workflow result may be used for a genuine scan failure; report vulnerabilities clearly without disabling existing release/security gates.
- Test workflow syntax, permissions, tool compatibility and advisory parsing with fixture data before asking the owner to approve activation. Keep the security monitoring workflow separate from existing CI unless an integration is explicitly approved.
- Include findings in the owner's cross-project daily intelligence briefing with the repository name, checked commit, scan timestamp, severity, source links, what changed since the prior scan and recommended **review-only** next steps. Respect private-repository confidentiality and never publish vulnerability details or credentials from private projects to public outputs.
